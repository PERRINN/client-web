# PERRINN prototypes

The `/prototypes` area, labeled **Prototyping** in the app, is a visual lab for trying and comparing UI ideas before building production components. Visual studies use local or mock data. Explicitly approved functional pilots such as Team Radio use isolated Firebase paths documented in data-model.md. The former chat-bubbles experiment has been promoted to production chat.

## Structure and naming

Each prototype lives in its own folder under `src/app/prototypes/`, with a routed Angular component and a `metadata.md` containing `Name`, `Type`, `Description`, and `Status`. Add each prototype to the Prototyping catalog and routing when creating one.

Give each prototype a descriptive name based on its subject or design direction, such as `chat-bubbles` or `clear-slate`. Do not add sequence numbers. Use the name and description to distinguish alternatives. Use descriptive folder names, component names, and route paths as well.

Keep each experiment small, focused on one design or interaction question, self-contained, and ideally at or below 300 lines of code. Use scoped styles and local state so a prototype can be changed or removed without affecting production components.

Statuses are `EXPERIMENT`, `CANDIDATE`, `SELECTED`, `REJECTED`, and `ARCHIVED`. Update the metadata status as an idea is evaluated. A selected prototype is a design reference: implement the approved behavior in the appropriate production component and service, then keep or archive the prototype as a reference. Do not import prototype code into production as a shortcut.

## Prototypes

The catalog groups prototypes into **Team tools**, **Engineering pilots**, **Architecture maps**, **Mosaics**, and **Colour palettes**. Colour palette previews include previous/next controls to move through their category without returning to the catalog.

Layout prototypes are low-level structural wireframes for deciding page composition. Use a few standard UI labels for regions and components, such as Primary Navigation, Search, Page Title, Content Panel, and Composer. Represent content with neutral placeholder shapes; avoid realistic product data, names, dates, counts, and explanatory copy. Do not add responsive behavior descriptions: users inspect reflow by dragging the preview's right edge. Each layout preview should have keyboard width adjustment and container-based breakpoints so its layout responds to the simulated width independently of the browser window. Keep the layout easy to read, with clear grouping from the app UI specification's dark page and surface contrast, sparse borders, and enough space to distinguish hierarchy and component placement.

- **Architecture maps:** `app-wiring`, `data-model-map`, and `workflow-map` show the current source structure, persisted record relationships, and major client-to-server workflows.
- **Colour palettes:** `clear-slate`, `warm-graphite`, `deep-tide`, `quiet-plum`, `clay-ember`, and `night-signal` compare distinct surface and accent combinations using the same mock team home screen.

## Team Radio

`/prototypes/team-radio` is a functional team-wide push-to-talk experiment (#87), not specific to Greenpower. It uses existing sign-in, Realtime Database coordination and browser WebRTC audio. It is listed under Apps → Greenpower and links back to Apps. The `/prototypes/team-radio` URL is retained for existing bookmarks and active-radio navigation; the pilot is no longer listed in the prototype gallery. UI is limited to the roster with app-wide profile avatars, Enable talking and Talk. Space remains available for push-to-talk without a visible keyboard hint. No manual leave, mute, disable-talking or key-selector controls appear.

Ten active participant places include three optional speaking places. Signed-in users automatically join as listeners when the visible radio page has space, then claim Enable talking first come, first served. A full room displays Room full and automatically admits the user when capacity opens; there is no queue or Join button. Automatic admission waits for Auth, connectivity and the complete bounded roster. It never requests microphone access; blocked autoplay exposes Enable sound. No queue. Leaving the radio route, switching tabs or switching apps starts a three-minute away window. Transmission stops immediately, while listening and both places remain active where the browser permits it. A compact Radio countdown link appears on other PERRINN pages; returning to the visible radio page before expiry cancels the away window. Expiry or sign-out releases both places and stops microphone capture. Network loss does not extend an existing away deadline. A network disconnect immediately stops transmission and peer audio, shows Reconnecting, and preserves both places for a three-minute grace period. Connectivity returning within that period automatically restores the radio and speaking permission; a fresh press is required to transmit. After expiry, returning to the visible page automatically joins as a listener when space is available. Abrupt closure uses session-bound server offline marking plus stale-place recovery after three minutes, performed by connected signed-in clients every five seconds and before claims. This is eventual cleanup, not a guarantee of immediate removal after a crash or network loss. The newest joined tab controls an account's audio; older cleanup cannot remove its places.

Hold Talk or Space to transmit; release, lost pointer capture, tab blur, hidden page, disconnect, lost authorization or the 30-second cap stops transmission. Hiding the page starts the same away window and stops transmission; talking is disabled until the radio page is active again. A busy press never queues; release and press again. The sender emits a 100ms start beep into outgoing audio and local playback only after successful floor acquisition. A 180ms microphone delay buffers the opening syllable behind the beep. Normal release drains that buffer before releasing the floor. Space is fixed, with no saved key preference; text inputs, links, buttons, modifier shortcuts and repeated keydown events do not trigger the global binding. The Talk button supports held Space/Enter.

### Connectivity, performance and limits

Peer connections are prepared before Talk is enabled; only pairs involving a speaking reservation connect. At the full three-speaker/ten-person room this is at most 24 bidirectional peer connections across the room; each active speaker sends up to nine audio copies. Listeners do not need microphone permission. Microphone acquisition shares one pending request and reuses a live stream throughout navigation and reconnection within the grace window. Microphone capture is requested directly by Enable talking, before awaiting audio startup. iOS Home Screen web apps may still repeat permission prompts after reload/termination; the web app cannot persist or override the browser permission. Each speaker browser keeps its microphone stream open only while microphone-enabled and gates outgoing speech at the audio graph; closing the radio stops the capture tracks. Silent negotiated tracks can remain open to avoid reconnecting on every press.

The prototype uses Google's public STUN endpoint and has no user-facing connection settings or relay credentials. Joining uses the existing PERRINN sign-in session. Some mobile networks, firewalls and NATs require TURN; a managed relay and automatic short-lived credential delivery would need a separate infrastructure/backend proposal and approval. No relay service or credential issuer is provisioned by this prototype. Relay coverage and costs remain unverified.

Database region, network round trips and WebRTC routing affect responsiveness. The start beep and 180ms microphone buffer add a deliberate short lead-in. Validate press-to-beep and speech-to-heard latency on real desktop/mobile devices over Wi-Fi and mobile data, including TURN, before increasing capacity or relying on this trackside. This prototype does not promise Zello's background operation, locked-screen reliability, managed relay infrastructure, offline messages or delivery guarantees. Same-machine synthetic browser checks are functional checks, not a measured field latency/audio-quality result.
