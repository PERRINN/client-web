# PERRINN prototypes

The `/prototypes` area, labeled **Prototyping** in the app, is a visual lab for trying and comparing UI ideas before building production components. Prototypes normally use local or mock data. The chat-bubbles live-data exception is described below.

## Structure and naming

Each prototype lives in its own folder under `src/app/prototypes/`, with a routed Angular component and a `metadata.md` containing `Name`, `Type`, `Description`, and `Status`. Add each prototype to the Prototyping catalog and routing when creating one.

Give each prototype a descriptive name based on its subject or design direction, such as `chat-bubbles` or `clear-slate`. Do not add sequence numbers. Use the name and description to distinguish alternatives. Use descriptive folder names, component names, and route paths as well.

Keep each experiment small, focused on one design or interaction question, self-contained, and ideally at or below 300 lines of code. Use scoped styles and local state so a prototype can be changed or removed without affecting production components.

Statuses are `EXPERIMENT`, `CANDIDATE`, `SELECTED`, `REJECTED`, and `ARCHIVED`. Update the metadata status as an idea is evaluated. A selected prototype is a design reference: implement the approved behavior in the appropriate production component and service, then keep or archive the prototype as a reference. Do not import prototype code into production as a shortcut.

## Prototypes

The catalog groups prototypes into **Architecture maps**, **Chat**, **Mosaics**, and **Colour palettes**. Colour palette previews include previous/next controls to move through their category without returning to the catalog.

Layout prototypes are low-level structural wireframes for deciding page composition. Use a few standard UI labels for regions and components, such as Primary Navigation, Search, Page Title, Content Panel, and Composer. Represent content with neutral placeholder shapes; avoid realistic product data, names, dates, counts, and explanatory copy. Do not add responsive behavior descriptions: users inspect reflow by dragging the preview's right edge. Each layout preview should have keyboard width adjustment and container-based breakpoints so its layout responds to the simulated width independently of the browser window. Keep the layout easy to read, with clear grouping from the app UI specification's dark page and surface contrast, sparse borders, and enough space to distinguish hierarchy and component placement.

- **Chat:** `chat-bubbles` opens the most recent human conversation already loaded in the sidebar, then navigates to `/prototypes/chat-bubbles/:id` using the same `chain` identity as `/chat/:id`. It reads `PERRINNMessages` by `chain`, ordered by `serverTimestamp` descending, with an initial limit of 30 (100 for a `scroll` deep link) and 15 more on Load earlier, using the existing production index. It displays real subjects, participants, avatars, dates and images. Consecutive messages from the same sender share one visible name and avatar, with compact spacing and per-message timestamps; date and unread dividers start a new group. The composer sends real text and images through `UserInterfaceService.createMessage` and the existing `images/{timestamp}-…` upload convention; the existing backend verifies/enriches records. Drafts survive failed sends. Latest messages appears only beyond one message viewport from the bottom (at least 300px); automatic scrolling stops earlier to preserve the reader’s position. Clicking the subject or image in the chat header opens Chat details, with keyboard access and focus restored to the header on close. Chat details provides an inline Edit chat form for signed-in users to change the subject (1–60 characters) and choose/preview a new image before Save; Cancel leaves the chat unchanged. Image files upload only on Save. Updates use the existing message-based `chatSubject` and chat-profile-image fields and backend propagation, including the production image-change message in the conversation. Failed saves retain the draft. Chat events use a compact Home-inspired date/title summary in the header only while upcoming or ongoing. Message dividers and event dates share local-calendar formatting: Today/Yesterday, weekdays within six days, then compact dates with the year only outside the current year; events also use Tomorrow and nearby future weekdays. Full dates remain available on hover. Opening the summary focuses the Event section in Chat details, with a Join link for HTTP(S) meeting locations from five minutes before the start. Signed-in users can schedule or edit descriptions, native local dates/times, duration presets/custom hours, and locations. The editor labels the local timezone, preserves drafts on errors, detects stale edits, and confirms cancellation inline. Event fields and message-based saves remain production-compatible; cancellation stores equal start/end timestamps in the past. The prototype reads and advances only the authenticated user’s existing chat cursor as messages are reached in the visible, focused conversation. Updates are debounced, paused for hidden tabs, the navigation drawer, chat details and image previews, and saved transactionally without moving backwards or overwriting flags. Confirmed own messages from sends and chat/event actions are acknowledged even from Chat details after their server timestamp resolves, without skipping unseen incoming messages or unloaded history. These acknowledgements follow the same focus, account and retry protections. Closing an image preview resumes viewport scanning. The unread divider captures incoming unread activity at entry and remains fixed during the visit and across history loads; cursor failures offer retry. A single neutral tick beside the timestamp appears only on the signed-in user’s own messages whose existing `verified` field is true. It represents processing status only, not delivery, another person’s read receipt or an authorization guarantee. While Bubbles is open, both sidebar conversation lists navigate to `/prototypes/chat-bubbles/:id` and highlight the selected chat; elsewhere they retain production chat routing. Bubbles fills the normal chat viewport supplied by the shell, with no prototype back link or preview toolbar. Loading/error/empty states reflect live data. Replies are excluded. The standalone input-bar and team-feed studies have been removed; the composer remains part of Bubbles.
- **Architecture maps:** `app-wiring`, `data-model-map`, and `workflow-map` show the current source structure, persisted record relationships, and major client-to-server workflows.
- **Colour palettes:** `clear-slate`, `warm-graphite`, `deep-tide`, `quiet-plum`, `clay-ember`, and `night-signal` compare distinct surface and accent combinations using the same mock member-home screen.
