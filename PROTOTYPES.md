# PERRINN prototypes

The `/prototypes` area, labeled **Prototyping** in the app, is a visual lab for trying and comparing UI ideas before building production components. Visual studies use local or mock data. Explicitly approved functional pilots such as Team Radio use isolated Firebase paths documented in data-model.md. The former chat-bubbles experiment has been promoted to production chat.

## Structure and naming

Each prototype lives in its own folder under `src/app/prototypes/`, with a routed Angular component and a `metadata.md` containing `Name`, `Type`, `Description`, and `Status`. Add each prototype to the Prototyping catalog and routing when creating one.

Give each prototype a descriptive name based on its subject or design direction, such as `chat-bubbles` or `clear-slate`. Do not add sequence numbers. Use the name and description to distinguish alternatives. Use descriptive folder names, component names, and route paths as well.

Keep each experiment small, focused on one design or interaction question, self-contained, and ideally at or below 300 lines of code. Use scoped styles and local state so a prototype can be changed or removed without affecting production components.

Statuses are `EXPERIMENT`, `CANDIDATE`, `SELECTED`, `REJECTED`, and `ARCHIVED`. Update the metadata status as an idea is evaluated. A selected prototype is a design reference: implement the approved behavior in the appropriate production component and service, then keep or archive the prototype as a reference. Do not import prototype code into production as a shortcut.

## Prototypes

The catalog groups prototypes into **Team tools**, **Engineering pilots**, **Architecture maps**, **Mosaics**, and **Colour palettes**. Colour palette previews include previous/next controls to move through their category without returning to the catalog.

Layout prototypes are low-level structural wireframes for deciding page composition. Use a few standard UI labels for regions and components, such as Primary Navigation, Search, Page Title, Content Panel, and Composer. Represent content with neutral placeholder shapes; avoid realistic product data, names, dates, counts, and explanatory copy. Do not add responsive behavior descriptions: users inspect reflow by dragging the preview's right edge. Each layout preview should have keyboard width adjustment and container-based breakpoints so its layout responds to the simulated width independently of the browser window. Keep the layout easy to read, with clear grouping from the app UI specification's dark page and surface contrast, sparse borders, and enough space to distinguish hierarchy and component placement.

- **Architecture maps:** `app-wiring`, `data-model-map`, and `workflow-map` show the current source structure, persisted record relationships, and major client-to-server workflows.
- **Colour palettes:** `clear-slate`, `warm-graphite`, `deep-tide`, `quiet-plum`, `clay-ember`, and `night-signal` compare distinct surface and accent combinations using the same mock team home screen.

## Team Radio

`/prototypes/team-radio` is a functional team-wide push-to-talk experiment (#87), not specific to Greenpower. It uses existing sign-in, Realtime Database coordination and browser WebRTC audio. It is listed under Apps → Greenpower and links back to Apps. The `/prototypes/team-radio` URL is retained for existing bookmarks and active-radio navigation; the pilot is no longer listed in the prototype gallery. UI is limited to the roster with app-wide profile avatars, Enable talking and Talk. Space remains available for push-to-talk without a visible keyboard hint. Leave stops listening and releases both places; Listen explicitly starts listening again. No mute, disable-talking or key-selector controls appear.

Ten active participant places include three optional speaking places. Signed-in users automatically join as listeners when the visible radio page has space, then claim Enable talking first come, first served. A full room displays Room full and automatically admits the user when capacity opens; there is no queue or Join button. Automatic admission waits for Auth, connectivity and the complete bounded roster. It never requests microphone access; blocked autoplay exposes Enable sound. No queue. Leaving the radio route, switching tabs or switching apps releases Talk immediately while retaining listening and both places for as long as the browser allows the connected session. Other PERRINN pages show a compact Radio link in the existing navigation row; only disconnect recovery shows a countdown. Leave or sign-out stops audio and microphone capture and releases both places. Leave prevents automatic readmission until Listen is selected. Optional Audio Session API hints request playback for listeners and switch to play-and-record before requesting a microphone, retaining recording mode through permission prompts and concurrent audio resumes. A rejected request restores playback; close restores the prior type. Unsupported APIs do not prevent listening. These hints do not grant background execution or guarantee that audio resumes after a silent gap. A network disconnect immediately stops transmission and peer audio, shows Reconnecting, and preserves both places for a three-minute grace period. Connectivity returning within that period automatically restores the radio and speaking permission; a fresh press is required to transmit. After expiry, returning to the visible page automatically joins as a listener when space is available. Abrupt closure uses session-bound server offline marking plus stale-place recovery after three minutes, performed by connected signed-in clients every five seconds and before claims. This is eventual cleanup, not a guarantee of immediate removal after a crash or network loss. The newest joined tab controls an account's audio; older cleanup cannot remove its places.

Hold Talk or Space to transmit; release, lost pointer capture, tab blur, hidden page, disconnect, lost authorization or the 30-second cap stops transmission. Hiding the page stops transmission; talking is disabled until the radio page is active again. A busy press never queues; release and press again. The sender emits a 100ms start beep into outgoing audio and local playback only after successful floor acquisition. A 180ms microphone delay buffers the opening syllable behind the beep. Normal release drains that buffer before releasing the floor. Space is fixed, with no saved key preference; text inputs, links, buttons, modifier shortcuts and repeated keydown events do not trigger the global binding. The Talk button supports held Space/Enter.

### Connectivity, performance and limits

Issue [#92](https://github.com/PERRINN/client-web/issues/92) investigation: [initial source audit](audits/team-radio-instability-2026-10-21.json) and [recovery/device-selection validation](audits/team-radio-recovery-2026-10-21.json). The initial audit reproduced uncapped failed-peer recreation and old-offer replay. Follow-up tests cover capped recovery and automatic same-account device takeover; the initiating cause of the reported mobile-data outage remains unconfirmed without device timelines.

Opening or focusing the radio does not replace a current same-account session on another device, including its existing three-minute offline recovery grace. The inactive device shows **On another device** and **Use here**; only that explicit action moves the reservation here and rejoins as a listener. The displaced device stops audio and waits rather than automatically taking the radio back. Same-tab reload recovery still requires the saved session to match the current server session. Expired own reservations can be admitted automatically. This is client interaction behavior, using existing ownership rules; it introduces no trusted device lock or new authentication policy. Two genuinely simultaneous first admissions can still race before either device receives the other's reservation, but the displaced device must not repeatedly reclaim it.

Media recovery retains unaffected connections. A failed peer remains represented through room updates; either side can issue a fresh ICE-restart offer. Higher-seat peers roll back a colliding local offer while lower-seat peers retain theirs, following the [WebRTC negotiation pattern](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Perfect_negotiation). Each side has three automatic retry slots per latest local/remote session pair, delayed 1, 3 and 8 seconds. Connected state cancels pending timers but does not replenish retry slots. A brief disconnected state gets five seconds to recover naturally; initial/stalled negotiation has a 25-second watchdog. After exhaustion, only that peer's transport closes and Reconnect is required. Temporary presence gaps retain attempt/consumed-offer history per fixed seat; canceling a reserved retry consumes its slot. Departure, sign-out, local-session replacement and disposal cancel timers and pending gathering waits. At most four distinct remote offers are accepted per session pair; consumed offer IDs prevent stale-mailbox replay. With the initial lower-seat offer and three retries per side, each pair can publish at most seven offers and seven answers (14 signaling writes), before SDK-level transport retries. At full capacity this is 336 application signaling writes across 24 pairs for fixed session identities, excluding presence/floor/cleanup. Session changes start new budgets; total session churn is not globally bounded. Refresh both clients after release; older clients do not support higher-seat recovery offers. No TURN infrastructure, Firebase rules, persisted fields or Functions change.

For a field diagnostic capture, run `sessionStorage.setItem('perrinn.teamRadio.diagnostics', '1')` in the browser console and reload before opening the radio. Enable console preservation across reload if needed, then reproduce on two accounts for at most two minutes or until the first failure. Each scoped service keeps the latest 200 local events and prints only its first 200 console events when enabled. Correlate `[Team Radio]` UTC timestamps, seat/session/offer IDs, Firebase connectivity and WebRTC ICE/signaling/connection transitions. No account IDs, names, SDP, candidate IPs, audio or credentials are logged; nothing is uploaded. Reload to start another capture. Disable with `sessionStorage.removeItem('perrinn.teamRadio.diagnostics')` and reload. Remote browser inspection may be needed on a phone. These diagnostics require releasing the changed client before testing the hosted app.

Intentional exit marks the local session inactive and completes media teardown before writing cleanup, because RTDB dispatches optimistic local listener events synchronously. Cleanup must not trigger outage recovery or a second exit.

Talk errors also expose **Copy details**, without requiring console capture. Reproduce one failed press/release, copy the details before Reconnect and share them explicitly for investigation. Clipboard export is `{version: 1, capturedAt, events}` containing the current 200-event local buffer; it is never uploaded automatically. It separates Enable talking microphone setup, speaking-slot claims and disconnect-hook failures, as well as acquisition, canceled/busy attempts, committed leases, outgoing-media failure, late cleanup, release and heartbeat rejection. Every export appends a current-state snapshot (joined listener/speaker, connection, microphone readiness and whether an error is visible), so a trace with no Talk attempt still shows the capture context. Talk records contain client-observed seat ownership, speaker reservation, session/presence checks, heartbeat age, estimated server offset/time, requested lease timestamps, transaction callback count and elapsed time. These are cached client observations: Firebase returns only permission denial, so they cannot establish the exact failed server rule or prove the state at rejection. No account IDs, names, tokens, raw errors, audio or candidates are exported. Copy success/failure leaves the original error intact. Error normalization handles uncoded SDK `permission_denied` messages while preserving microphone errors. Skipped heartbeat transactions distinguish empty local cache from a different session without reviving either. No extra queries, subscriptions or automatic retries are added; existing acquisition/release/token-cleanup work is retained. Canceled presses no longer report Channel busy, and late transaction/heartbeat failures cannot overwrite a newer session's error. Failed release stops microphone output immediately; server leases remain capped at 30 seconds. Rules, persisted data and Functions are unchanged. This diagnostic release does not claim to resolve the underlying Talk denial. See [Talk diagnostics validation](audits/team-radio-talk-diagnostics-2026-10-21.json).

Peer connections are prepared before Talk is enabled; only pairs involving a speaking reservation connect. At the full three-speaker/ten-person room this is at most 24 bidirectional peer connections across the room; each active speaker sends up to nine audio copies. Listeners do not need microphone permission. Microphone acquisition shares one pending request and reuses a live stream throughout navigation and reconnection within the grace window. Microphone capture is requested directly by Enable talking, before awaiting audio startup. iOS Home Screen web apps may still repeat permission prompts after reload/termination; the web app cannot persist or override the browser permission. Each speaker browser keeps its microphone stream open only while microphone-enabled and gates outgoing speech at the audio graph; closing the radio stops the capture tracks. Silent negotiated tracks can remain open to avoid reconnecting on every press.

The prototype uses Google's public STUN endpoint and has no user-facing connection settings or relay credentials. Joining uses the existing PERRINN sign-in session. Some mobile networks, firewalls and NATs require TURN; a managed relay and automatic short-lived credential delivery would need a separate infrastructure/backend proposal and approval. No relay service or credential issuer is provisioned by this prototype. Relay coverage and costs remain unverified.

Database region, network round trips and WebRTC routing affect responsiveness. The start beep and 180ms microphone buffer add a deliberate short lead-in. Validate press-to-beep and speech-to-heard latency on real desktop/mobile devices over Wi-Fi and mobile data, including TURN, before increasing capacity or relying on this trackside. This prototype does not promise Zello's background operation, locked-screen reliability, managed relay infrastructure, offline messages or delivery guarantees. Same-machine synthetic browser checks are functional checks, not a measured field latency/audio-quality result.
