# PERRINN prototypes

The `/prototypes` area, labeled **Prototyping** in the app, is a visual lab for trying and comparing UI ideas before building production components. Visual studies use local or mock data. Functional pilots use the isolated Firebase paths documented in data-model.md. The former chat-bubbles experiment has been promoted to production chat.

## Structure and naming

Each prototype lives in its own folder under `src/app/prototypes/`, with a routed Angular component and a `metadata.md` containing `Name`, `Type`, `Description`, and `Status`. Add each prototype to the Prototyping catalog and routing when creating one.

Give each prototype a descriptive name based on its subject or design direction, such as `chat-bubbles` or `clear-slate`. Do not add sequence numbers. Use the name and description to distinguish alternatives. Use descriptive folder names, component names, and route paths as well.

Keep each experiment small, focused on one design or interaction question, self-contained, and ideally at or below 300 lines of code. Use scoped styles and local state so a prototype can be changed or removed without affecting production components.

Statuses are `EXPERIMENT`, `CANDIDATE`, `SELECTED`, `REJECTED`, and `ARCHIVED`. Update the metadata status as an idea is evaluated. A selected prototype is a design reference: implement the approved behavior in the appropriate production component and service, then keep or archive the prototype as a reference. Do not import prototype code into production as a shortcut.

## Prototypes

The catalog groups prototypes into **Team tools**, **Engineering pilots**, **Architecture maps**, **Mosaics**, and **Colour palettes**. Colour palette previews include previous/next controls to move through their category without returning to the catalog.

Layout prototypes are low-level structural wireframes for deciding page composition. Use a few standard UI labels for regions and components, such as Primary Navigation, Search, Page Title, Content Panel, and Composer. Represent content with neutral placeholder shapes; avoid realistic product data, names, dates, counts, and explanatory copy. Do not add responsive behavior descriptions: users inspect reflow by dragging the preview's right edge. Each layout preview should have keyboard width adjustment and container-based breakpoints so its layout responds to the simulated width independently of the browser window. Keep the layout easy to read, with clear grouping from the app UI specification's dark page and surface contrast, sparse borders, and enough space to distinguish hierarchy and component placement.

- **Architecture maps:** `app-wiring`, `data-model-map`, and `workflow-map` show the current source structure, persisted record relationships, and major client-to-server workflows.
- **Colour palettes:** `clear-slate`, `warm-graphite`, `deep-tide`, `quiet-plum`, `clay-ember`, and `night-signal` compare distinct surface and accent combinations using the same mock team home screen.

## Voice input

`/prototypes/voice-input` is the functional speech-capture pilot for #99, listed under Team tools with a microphone/transcript graphic tile. Any signed-in user can press anywhere on the microphone pill (including its waveform and PERRINN logo), or use Space or Enter once to start recording and again to stop, transcribe and privately save the result. Touch activation fires once after 120 ms while still held, with no movement beyond 10 CSS pixels; releasing never triggers another action, preventing quick taps and swipes from opening or closing the microphone. The compact fixed dock retains its waveform and footprint during startup, recording and submission. Results append local conversation replies, and the control becomes ready again after success or failure. Escape, blur, hiding, navigation and sign-out discard unfinished capture; a second activation during pending permission cancels startup. One short higher bip opens the mic and one slightly lower bip signals closing; capture excludes their generated audio path. Permission failures and background interruptions stay silent. Each recording is capped at 30 seconds. See the data-model guide for current per-user submission budgets and validation limitations.

This pilot captures input only; it does not interpret intent or publish messages. Audio goes to OpenAI through the authenticated backend and is never retained in PERRINN storage. See [Voice input prototype](data-model.md#voice-input-prototype) for persisted paths, security rules, request/work budgets, retention, costs, setup, release order and validation limitations. Build the frontend and backend locally without calling the real provider; a hosted round trip requires separately authorized rule/function/client deployment and a configured server-side secret.

## eChook connection

`/prototypes/echook-connection` is a local hardware experiment under Engineering pilots. It targets the paired eChook HC-05 **Bluetooth Classic SPP** module on the Redmi Note 14, using Web Serial in Android Chrome (Bluetooth RFCOMM support was introduced in Chrome 138). It does not use BLE. Feature detection checks the secure context and serial API; actual device compatibility still requires the workshop test. Safari/iPhone does not support this connection path.

On the Android phone, use an up-to-date Chrome over HTTPS, enable **Settings → Keep screen on** for an ordinary browser tab, and power the car's eChook. Pair it in Android settings if necessary. In OMNI choose **Close** from its menu: switching away can leave its background service holding the connection. Open the prototype, press **Connect**, and select eChook in the browser chooser. The dashboard displays vehicle speed in mph, Battery left, Battery right, throttle input (`t`) in percent, motor speed (`m`) in rpm, current (`i`) in amps, ambient temperature (`a` / Temperature 1) and motor temperature (`b` / Temperature 2) in °C, matching the Greenpower telemetry page, and the phone’s local time of day (HH:mm:ss, including while disconnected). As on Greenpower telemetry, Battery left uses the lower-battery channel (`w`) and Battery right is total voltage (`v`) minus lower voltage. Compare these values with OMNI in separate runs. Leave the page or close the tab before returning to OMNI. A deployed page requires separately authorized Hosting deployment; the local build alone does not make this route available at perrinn.com. Remote plain HTTP LAN addresses cannot use this secure-context API.

The page receives only and never requests a writable stream or changes firmware/calibration. Decoding follows [firmware channel identifiers](https://github.com/eChook/eChook-Arduino-Nano/blob/master/eChookCode/Globals.h) and [packet construction](https://github.com/eChook/eChook-Arduino-Nano/blob/master/eChookCode/eChook_Functions.ino), including current zero bytes and the [legacy zero sentinel](https://docs.echook.uk/bluetooth-communication/bluetooth-packet-encoding). It handles fragmented packets and resynchronizes after invalid frames. The decoder retains unknown printable channel IDs without inferred units; the dashboard displays only the eight selected sensor readings. Negative/signed extensions and customized channel definitions are not established by the reference protocol; readings need comparison with the installed firmware before relying on them.

One explicitly selected serial connection runs until page navigation or pagehide. There is one pending read, no automatic reconnect/retry, a 4 KiB serial buffer, at most four partial packet bytes and one latest reading for each of at most 94 printable channel IDs. Serial UI updates occur twice per second; a page-scoped one-second clock updates phone-local time and freshness while disconnected too, and unsubscribes on navigation. Sensor panels retain a fixed footprint through connection, loading, stale, error and disconnected states. Missing, disconnected or more-than-five-second-old readings display a dash with an accessible status and hover title; no connected/status banner is displayed; zero remains a valid reading. Calculating Battery right requires both voltage inputs to be present and fresh because serial fields arrive individually. A new connection clears previous readings. There is no sample history, GPS, recording, upload, voice integration, Firebase access or persistent browser storage in this prototype. The normal app shell retains its existing service behavior. Backend, data contracts and security rules are unchanged.

Validation: `node --test scripts/echook-connection.test.mjs`, `npm run build`, `npm run lint`. `PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs node scripts/echook-connection-ui.mjs` runs the real Angular page/gallery without Firebase initialization and with a synthetic serial stream; it checks six desktop/portrait/landscape sizes in the real app shell (down to 320px wide and 280px tall), no scrolling or clipped metric content (including panel bounds inside the visible viewport), reduced visual viewport heights, entry from a scrolled gallery, in-place rotation without reconnecting, mph/battery calculations, throttle/RPM/current values, phone-local clock updates, graphic tile/route, keyboard focus, stable action geometry, live/stale/disconnected states, unsupported browsers and navigation cleanup. Optional `PLAYWRIGHT_CHANNEL` defaults to `chrome`. On 24 October 2026, Nico confirmed that the deployed prototype connects to eChook and receives all live values on the Redmi. The new dashboard layout still needs confirmation on that phone; automated browser checks do not prove race-session stability or calibration. Chat voice coexistence is outside this first test.

The eChook dashboard uses eight sensor panels in the available shell viewport, with two columns and four rows in portrait, and four columns and two rows on short landscape screens. The phone clock occupies one compact row. Connect appears only before connection or after failure, with errors shown only when needed. At Nico’s request there is no back-to-Prototyping link, connected banner or Disconnect button; use the normal shell navigation or browser Back to leave. Speed, RPM, current and time omit visible labels; Battery left, Battery right, Throttle, Ambient temp and Motor temp retain theirs. Every value keeps an accessible name. Route-scoped App component styles give only this page full content height; the shell’s sidebar, mobile header and other routes retain their existing layout.

The component measures its available height against both the shell content boundary and `window.visualViewport` (falling back to the window height), updates after resize/visual-viewport events using one coalesced animation frame, and resets inherited main-container scrolling on entry. A parent ResizeObserver tracks shell sizing. Observers/listeners and pending frames are removed on navigation. Container queries choose the two-by-four or four-by-two sensor grid from actual available dimensions; values scale within those panels rather than hiding overflow. Automated visible-viewport checks simulate browser-bar height loss, but the final physical-phone layout still needs confirmation.
