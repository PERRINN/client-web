# Data and workflow map

This is a source-based map of the data currently used by the client and Cloud Functions. It is an orientation guide, not a complete schema or a promise that every historical document has the fields listed here. Documents in `PERRINNMessages` are polymorphic and their shape depends on the workflow. Before changing a field or path, search all readers and writers and check the Firebase rules and Functions.

## Main data paths

| Path | Purpose and common fields | Main readers and writers |
| --- | --- | --- |
| `PERRINNMessages/{messageId}` | Shared message/event/profile/payment ledger. Common fields include `user`, `chain`, `text`, `serverTimestamp`, `verified`, and `verifiedTimestamp`. Depending on message type, also includes `purchaseCOIN`, `transactionIn`/`transactionOut`, `fund`, event fields, recipient data, and image references/URLs. | Client writes through `UserInterfaceService.createMessage`; chat, team, profile, settings and PRN pages read it. `dbMessagesOnCreate` and `verifyMessage` mark and enrich records. Payment and scheduled Functions can create records through `createMessageAFS`. Image finalization updates image URL fields. |
| `userPresence/{userId}` | Public recent app activity: `lastActiveAt` (Firestore server timestamp). One document per authenticated user. | App-wide `PresenceService` writes the current user’s timestamp; Home displays the latest ten other users and resolves only their profiles; profile pages and chat side profiles listen to the focused user’s presence document. |
| `lastSeen/{userId}/chats/{chain}` | Per-user read cursor: `messageId`, `serverTimestamp`, `updatedAt`. | Chat reads and advances the current user's cursor; profile uses per-document listeners only for loaded conversation chains to calculate unread state and flags. |
| `PERRINNTeams/{userId}/payments/{orderId}` | Revolut order/payment tracking. Includes provider/order/reference/user, currency and charge/PRN amounts, normalized `status`, provider payload in `source`, and processing timestamps/flags such as `purchaseMessageCreated`. | PRN page observes a payment doc. `revolutWebhook` and `syncRevolutOrderStatus` write status. `dbTeamPaymentsOnCreate` creates a purchase message once a successful payment is observed. |
| `Images/{imageId}` | Image metadata and generated `imageUrlThumb` / `imageUrlMedium` values. Message records point at images by timestamp-like ID. | `verifyMessage` reads image metadata; `storageOnFinalise` writes resized URLs and patches linked messages. |
| `Integrations/googleDriveActivityState` and `Integrations/githubActivityState` | Scheduler cursors/state for external activity polling. | `driveFolderActivity` and `githubActivity` Functions. |

Cloud Storage uploads currently use `images/...` object names. Chat and account settings upload there; the storage finalization Function derives image metadata and updates Firestore. The Team Radio prototype uses the isolated Realtime Database `/teamRadio/team` subtree; its paths, authorization and lifetimes are documented in [Team Radio prototype](#team-radio-prototype-realtime-database). Other Realtime Database paths remain default-deny in `database.rules.json`.

## Important workflows

### Message creation and verification

1. The client calls `UserInterfaceService.createMessage`, adds the authenticated user, profile defaults, and a server timestamp, then writes to `PERRINNMessages`.
2. `dbMessagesOnCreate` invokes `verifyMessage` for each created message. Verification may link user timeline messages, resolve profile/image data, update the latest message for a chat, normalize financial subobjects, and set `verified` plus `verifiedTimestamp`. New backend messages created by `createMessageAFS` have `isBackendMessage: true`; verification retains an explicit `true` and otherwise writes `false` on the newly processed record. This classification is not inherited from preceding messages. The existing “(Backend message)” suffix is retained. No historical records are backfilled, and no Firebase access rules change. The classification is a presentation field, not an authorization or trusted-origin guarantee; the existing rules do not restrict client values for it.
3. Team, profile, chat and wallet UI query these verified records. Chat uses `chain` plus `serverTimestamp`; profiles use the user's latest verified message; Team queries latest contributor records using `userChain.nextMessage` and `wallet.balance`.

Do not assume all message documents are plain chat text. `PERRINNMessages` is also used for user profile snapshots, chat state, events, funds, transactions and PRN purchase credits.

Production chat lives in `src/app/chat/` and preserves the existing chain identity and message creation/upload contract. Its history query has an explicit result limit that grows on Load earlier; it is an expanding subscription, not a fixed total session-work bound. It advances the authenticated user’s existing cursor when messages are reached in the visible, focused conversation, using a transaction and merge to preserve manual flags and prevent older updates from moving it backwards. Successful local sends and chat/event actions publish their confirmed message IDs to the open chat’s read session. Once the existing history snapshot resolves their server timestamps, these own messages can advance the cursor even while Chat details hides the conversation, but only in the focused, visible app and without skipping unread incoming messages or a gap outside the loaded history window. Pending timestamps, cursor failures and concurrent writes retain acknowledgements for retry; changing account/chat clears them. Closing an image preview triggers another viewport scan. The unread divider captures an incoming message at entry and stays fixed for the visit; subsequent own actions cannot create it. Its event editor uses the same `eventDescription`, `eventDateStart`/`eventDateEnd` epoch milliseconds, `eventDuration` hours and `eventLocation` fields as the existing event contract. Scheduled event messages include the description, date/time with the author’s local timezone, duration and location. Edit messages include only changed fields and their new values; cancellation messages identify the event by description. Long description/location text is shortened to respect the existing 500-character message limit; event fields retain their full values. Cancellation uses equal start/end values in the past, preserving the existing propagation contract. Dates/times are edited in the viewer’s local timezone; no timezone field is added. Its own-message verification tick reflects the existing `verified` processing field only. See [ui-spec.md → Production chat](ui-spec.md#production-chat) for the user workflow and limits.

### PRN Contribution Credits

PRN records and recognises contributions to PERRINN projects. Client copy uses **PRN Contribution Credits**, **PRN Credits** or **PRN**, and calls participants contributors. Contributions may include time, funds, hardware, services or software from individuals and companies. This terminology change covers existing flows; it does not add structured in-kind declarations or credit valuation/approval workflows.

Participation is open and independent of PRN balances or payments. The accounting calculations for `wallet.balance`, `purchaseCOIN`, `transactionIn`/`transactionOut`, `contract`, `interest` and `locking` remain unchanged. `verifyMessage` no longer computes, writes or returns `membership`. Historical membership fields and messages are retained without backfill and ignored by the client. Daily statistics omit `membersCount`; displays use the existing `statistics.userCount`, which counts processed profiles, not all Authentication accounts. The daily wallet refresh retains its deployed `scheduledDailyMembership` export and file name for operational compatibility, but no longer reads thresholds or publishes membership counts. It enumerates all Authentication pages (1,000 users per page), including a single page with no continuation token. Reverification of a historical document does not delete its old fields. No legacy field is used as an access signal.

The Team queries latest verified contributor profiles with `wallet.balance > 0`, ordered by balance descending, in cursor-paginated reads of up to 200 profiles. This is a team filter, not a participation or access requirement. Name-and-bio search filters loaded profiles and preserves the balance-descending order; Load more fetches the next page using the unchanged balance-ordered cursor. Both card and list views open the existing profile route. Each visit starts a fresh snapshot; pages are fetched on demand rather than keeping live subscriptions to every loaded profile. This uses the existing I59 index; no indexes are added or deleted. Funding presets are 10, 25, 50, 100 and 250 in the selected currency, independent of historical thresholds. Existing currency rates convert the selected payment into PRN credits. Authentication, payment metadata, Firebase rules and independent contract approval checks remain unchanged. These backend changes require a Functions deployment; local changes do not update the live scheduled job.

The [Team performance investigation](audits/team-performance-2026-10-16.md) records measurements and validation for issue #83. The tested smaller batch was reverted; the original 200-profile limit remains, and the reported delay's cause is unconfirmed.

Profiles show existing credited hours (`contract.hoursTotal`) and funding-credit provenance (`purchaseCOIN.amountCummulate`) where present. History labels distinguish funding credits, transfers, balance adjustments and time credits; the time agreement/signature mechanism and declaration validation remain unchanged. Historical message text is not rewritten. Public visibility is unchanged; see the access-policy findings below rather than assuming privacy from the contribution-ledger terminology.

The existing `interest` calculation is presented as a balance adjustment. The profile's balance illustration retains the current formula and states that rates may change; it promises no investment return. PRN grants no ownership or profit entitlement; future profit sharing is only a possibility, not a current right or promise. No historical data migration, rule change or index change is required. `/buyPRN/:id`, payment metadata, pending-payment storage and transfer links remain compatible.

### Project funding and PRN credits

1. The PRN page calls the `createRevolutOrder` HTTPS Function and receives an order/checkout URL.
2. The page tracks `PERRINNTeams/{userId}/payments/{orderId}` and periodically requests a status sync through `syncRevolutOrderStatus`.
3. Revolut's `revolutWebhook` also writes payment status to the same payment document.
4. When `dbTeamPaymentsOnCreate` sees a successful transition, it creates a `PERRINNMessages` record with `purchaseCOIN`, then marks the payment with `purchaseMessageCreated`.
5. The message verification path processes that record; the PRN page watches for the verified purchase message before showing completion.

When changing this flow, trace the client, both status writers, the payment trigger, and message verification together. The order document is not the only record involved in a completed credit.

### Chat fund updates

Chat uses the existing `PERRINNMessages.fund` contract: client commands contain `description`, `amountGBPTarget` and `daysLeft`. `amountGBPRaised` and derived fields are inherited/enriched by `functions/utils/verifyMessage.js`; the Chat editor does not write raised totals. Targets convert from the viewer’s configured currency to GBP using the existing `currencyList.*.toCOIN` rates, with an explicitly labelled GBP fallback if rates are unavailable. An unchanged target preserves its stored GBP value across display-currency rounding.

Cancellation preserves the legacy nonzero marker (`amountGBPTarget: 0.0001`, `daysLeft: 0.1`, description `add a description`) because zero values fall back to prior state in the verifier. Existing fund views and Chat hide targets below £0.01; the verifier may still mark this sentinel active. This sentinel is technical debt retained for compatibility, not a pattern for new workflows. Replacing it requires an approved client/server data-contract migration with regression coverage for cancellation, inherited fund state and existing records. Days remaining reflect the verifier’s recorded `daysLeft`, including its elapsed-days subtraction and rounding on message verification; this client change does not introduce a new deadline or change that calculation. Funds and totals are read from the already-loaded chat snapshot without additional queries. Existing authorization and public-read policy remain unchanged.

### Images

Client uploads go to Cloud Storage under `images/`. Legacy chat and Settings use `ImageUploadService` for transport/progress reporting, preserving their timestamp-prefixed object names and message fields; upload progress is local UI state and is never persisted. Message fields such as `userImageTimestamp`, `chatImageTimestamp`, and `chatProfileImageTimestamp` associate an upload with a message/profile role. `storageOnFinalise` writes thumbnail/medium URLs into `Images/{imageId}` and patches matching `PERRINNMessages` documents. Keep those identifiers and role-specific URL fields aligned across client and Function code.

## Access policy as currently written

- Firestore's recursive public-read grant now excludes the new `GreenpowerTelemetry` root collection. That collection requires Firebase Authentication for all reads and denies client writes except the validated admin view settings described below; its HTTPS ingestion Function writes through Admin SDK. Other Firestore collections retain their existing public-read behavior. The narrower `lastSeen` read/write clauses do not override the broad grant for those other collections. Message creation has a separate owner/timestamp/text-length check; there is no matching client update/delete grant in the shown rules. These are repository rules; deployment is a separate operation.
- Storage rules allow public reads and authenticated writes to every object.
- Realtime Database rules allow authenticated reads of radio state within the isolated `/teamRadio/team` subtree, with ownership, session and field validation on writes. Signaling reads are restricted to the recipient account. All other paths remain default-deny. See [Team Radio prototype](#team-radio-prototype-realtime-database) for the detailed access contract and lifetimes.
- Cloud Functions use Admin SDK access, which bypasses client Firestore rules; authorization and validation for their HTTPS endpoints must be evaluated in the Function itself.

These are observations of the checked-in rules, not a recommendation to change access. Treat any rules or authorization change as security-sensitive and review its user impact before implementation.

### Proposed least-privilege read policy — 2026-10-15

**Investigation and proposal only. Not implemented or approved for deployment.** No production documents or deployed rules were read during this investigation. Findings below follow the checked-in readers, writers and rules; they establish a source-level exposure, not a confirmed production breach. `firestore.rules`, Functions, application code, indexes and persisted data remain unchanged.

#### Why narrowing the wildcard alone is insufficient

The recursive `allow read;` makes all document reads and queries public, including per-user cursors, provider payment payloads and scheduler state. An overlapping owner rule cannot revoke this permission. The `lastSeen/{userId}/payments/{payment}` clause is also misplaced: real orders live under `PERRINNTeams/{userId}/payments/{orderId}`, and its `team` identifier is not defined. No current client/server reader or writer for the misplaced path was found.

More seriously, public feed documents already mix public content and private account data:

- [verifyMessage.js](functions/utils/verifyMessage.js) lines 82–87 obtains or inherits `emails.auth` and can use it to update the user's Authentication email; line 305 writes `emails` onto the message. This runs for ordinary chat/profile/payment messages, not only account-setting commands. A `verified == true` public-read condition would still disclose the email.
- The same verifier stores `transactionPending.code` and `reference` (lines 181–186), plus financial and contract state. [dbTeamPaymentsOnCreate.f.js](functions/dbTeamPaymentsOnCreate.f.js) writes `source.email` on payment records and writes an order identifier as `purchaseCOIN.chargeID` on the shared ledger. Removing public payment-document access alone does not hide the ledger's copy of that identifier. The verifier also puts a transaction reference into generated message text (around line 324), so deleting nested fields alone is insufficient.
- Settings sends email-change commands through the shared collection and reads `emails.auth` back from the latest user message. Public pages consume many of the same documents. Merely removing an email field would break that private account workflow and the verifier's inherited state unless its readers/writers are migrated together.

Firestore grants reads at document granularity; it cannot redact selected fields. Queries must satisfy the rules for their potential results, rather than relying on client-side filtering. See [field access](https://firebase.google.com/docs/firestore/security/rules-fields), [query rules](https://firebase.google.com/docs/firestore/security/rules-query), and [overlapping matches](https://firebase.google.com/docs/firestore/security/rules-structure#overlapping_match_statements).

#### Compatibility inventory

| --- | --- | --- |
| Home images/events/funds and sidebar/automatic updates | Public `PERRINNMessages` queries in `homeFeed.service.ts` and `sidebarConversations.service.ts`; image limit 50, event/fund pages 50, human sidebar pages 30, automatic list 15 | Anonymous access to approved public documents; retain ordering, pagination and live updates |
| Public profile, histories, team and recipient search | `profile.component.ts`, `team.service.ts`, `presence.service.ts` and `chat.component.ts`; latest user records, `userChain`, name, wallet, recipient and event/fund filters | Public projection retains explicitly approved displayed fields and query keys; public wallet/contract fields need the decision below |
| Chat history and image gallery | `chat.component.ts` queries by `chain`, without a `verified` constraint; pagination and read markers use original message IDs | Public history reads sanitized public messages; retain IDs and timestamps. Sender-only pending feedback must be handled separately if needed |
| Shared app configuration | `userInterface.service.ts` reads latest PERRINN profile/admin records while signed out; currency conversion uses admin message fields | Public projection must include approved team profile, currency/rate and aggregate configuration; never expose the entire raw admin snapshot |
| Account state/settings and purchase-credit completion | Latest authenticated user's raw messages in `userInterface.service.ts`, `settings.component.ts`, `buy-prn.component.ts` | Owner-only raw account/message reads constrained by `user == request.auth.uid`; preserve private email and order linkage there |

| Recent activity | Public `userPresence` list/direct reads; owner writes only `lastActiveAt` | Explicit public reads and existing timestamp-only owner writes; this intentionally keeps recent activity public |

No current collection-group query was found. Client rendering, TypeScript interfaces, hidden settings controls and `recipientList` do not provide a security boundary. The existing recipient list selects and displays conversations; this proposal does not reinterpret it as private-chat membership or make public chats private.

#### Recommended implementation in two independently reviewed stages

**Stage A: narrow collection access without changing feed queries.** Remove the database-wide public grant. Add exact public reads for top-level `PERRINNMessages/{messageId}` and `userPresence/{uid}` only. Retain existing message-create and presence-write behavior for this containment step. Keep owner access to the current `lastSeen` root/chats paths, add owner-only `get` on the real payment path, and deny all other client paths by absence of a grant. Remove the unused misplaced payment clause after checking deployed/other-client compatibility. Do not use recursive public or owner matches that automatically include unknown subcollections.

The essential proposed read clauses are:

```text
PERRINNMessages/{id}:                  public get/list (temporary residual risk)
userPresence/{uid}:                    public get/list
lastSeen/{uid}:                        owner read/write (existing intent)
lastSeen/{uid}/chats/{chain}:          owner read/write
PERRINNTeams/{uid}/payments/{orderId}: owner get only; no client list/write
Images/*, Integrations/*, all others:  no client grant
```

Here “owner” means `request.auth != null && request.auth.uid == uid`, using the authenticated UID and the path, never a request-body `user` value. Document listeners must be tested with the get-only payment rule. Admin SDK processing bypasses these client rules, so this stage requires no Functions/schema change and should preserve current public feed behavior. It closes unnecessary cross-user/payment/state reads, but **does not solve embedded emails or other private values in the message ledger**. Do not describe Stage A as complete least privilege or make its residual exposure permanent. A temporary `verified` predicate is not recommended: chat lacks that filter, and verified documents themselves contain private fields.

**Stage B: separate public feed documents from the private ledger.** Recommended design: retain `PERRINNMessages` as the canonical private workflow ledger and publish a server-produced, explicitly allowlisted public projection. `PublicMessages/{originalMessageId}` is a proposed name, not an established or approved path. Keeping source records private avoids destroying historical ledger/account inputs while public reads move to sanitized documents. This stays within Angular/Firebase and needs no new infrastructure service.

- Only trusted server code publishes or removes public documents. Never spread a raw record into a public object or recursively copy financial objects. Map approved fields individually, including nested fields. Preserve original IDs, `chain`, timestamps, approved profile/media/event/fund fields, `userChain`/recipient query keys, and the approved public financial/configuration values required by existing views.
- Exclude emails, raw provider `source`, order IDs/charge IDs, redemption codes/references, private command payloads and unapproved account state. For generated administrative/payment text, construct a safe public summary; raw `text` and `chatSubject` can themselves contain sensitive references. User-authored public chat remains intentionally public. Do not publish private account commands simply because their text is short or the message is verified.
- Define trusted publication eligibility and a typed public DTO. Current client creation permits extra fields, including `verified` and `isBackendMessage`; neither flag is currently proof of server processing or safe disclosure. A public/private flag supplied by a client must not determine authorization. Tighten workflow submission contracts and prevent clients from assigning server-owned processing/publication/financial result fields before using them as trust signals. Existing command inputs such as `transactionOut` must be distinguished from computed results rather than banned indiscriminately.
- Keep anonymous reads for the new public projection and public presence. Deny client writes to projections. Restrict raw ledger reads to approved private needs, initially the author/owner for account state and credit tracking, with matching `user == auth.uid` query constraints. A recipient does not automatically gain access to an author's complete raw record and email. Resolve transaction-link access separately before cutover.
- Move public readers behind focused service contracts while retaining existing Angular routes and templates' required inputs. Update Home, profile, sidebar, team/search, chat/gallery, presence profile lookup, and shared team/admin configuration reads. Keep Settings/current-user private state and purchase-credit lookup on owner-authorized records. Do not point all `UserInterfaceService` reads at one public collection: it currently serves both public and private purposes.
- Publication must react to source changes after verification, including later image URL patches, daily reverification, latest-chat flips and deletions. A proposed new `publicMessageProjection.f.js` handler plus export in `functions/main.js` could isolate this responsibility; choose the exact mechanism only after backend review. Handle duplicate/out-of-order events by reconciling current authoritative state, remove no-longer-public documents, and never publish unverified raw values between lifecycle steps. Projection lag must not lose latest-chat rows or restore stale versions.
- Backfill only approved safe public fields using idempotent bounded batches, preserving IDs/history. Do not delete raw history to sanitize it. New projection queries need matching indexes, explicit result limits and pagination; existing unbounded event/fund/history queries must be paginated without truncating required results. Compare live/repository indexes before deployment and do not delete old ones until all old readers retire.

This stage changes persisted paths, client contracts and trusted server behavior. AGENTS.md requires approval of the schema/rules change **and a separate concrete explanation/approval of the affected Functions implementation before editing it**. None has been implemented here. Existing verifier, scheduler, payment trigger and storage writers need regression coverage even if a separate publisher leaves their business calculations unchanged. Payment HTTPS handlers must independently authorize identity/ownership and webhook authenticity; Firestore rules do not protect Admin-backed endpoints.

#### Product decisions required before Stage B

1. Keep the current public wallet balances, financial/contract summaries and histories, or deliberately reduce their visibility? **Recommended compatibility baseline:** retain currently displayed summaries only, subject to explicit confirmation; hide emails, provider details, identifiers and redemption secrets. These are nested field decisions, not approval to publish entire financial objects.
2. Are all current chat chains intended to remain public? The current implementation permits public reads; it has no trusted private-chat ACL. Keep that behavior for approved public content. Private chats, including historical access decisions, would be a separate authorized design.
3. What are the intended recipients/expiry/claim rules for pending transaction links? Preserve the supported claim workflow through a separately authorized details/claim contract; do not silently replace it with a broken owner-only raw-document read.

Historical private command text and arbitrary message bodies cannot be perfectly classified from this source inspection. Exact public-history parity cannot be promised until representative records are reviewed securely. Unknown or sensitive types should be withheld from publication pending review, with the public-content preservation criteria agreed before rollout.

#### Validation and rollout gates

No emulator tests or live authorization checks were run for this proposal: there is no changed ruleset or backend implementation to validate. The current root package has no Firestore rules test suite; use synthetic emulator fixtures for the approved implementation, never production customer records. Existing public audit self-tests are not rules authorization tests.

Rollout order after approvals: inspect the currently deployed rules/IAM without data reads; verify other consumers; test Stage A in emulators/staging; review/deploy Stage A on its own. For Stage B, approve the publication/field policy and specific backend plan; deploy/test publisher and safe backfill, build required indexes, switch public readers, verify anonymous/owner/cross-user behavior, then remove public raw-ledger access. The period before final lockdown retains the old email exposure and must be an explicit, short transition. Do not promise zero exposure during that overlap.

Verify deployed rules and query behavior after each authorized release. Plan for stale clients and service-worker caches: they must update or show an explicit upgrade state after raw reads close. IndexedDB may retain previously downloaded records and any earlier public downloads cannot be recalled. A rollback must keep private boundaries closed, using the safe public projection or a compatible safe client; never restore the global wildcard to recover a feed. Historical backfill volume/cost, privacy response, cache cleanup and deployment scheduling need operational approval rather than being executed by this proposal.

## Query and maintenance notes

- `firestore.indexes.json` tracks all required composite indexes for the current client and Functions, including the backend-message sidebar query. See the [Firestore index audit](#firestore-index-audit) for query coverage, cleanup decisions, the original live export, and the maintenance workflow. Deploy required additions and wait for readiness before releasing dependent queries.
- Home at `/home` listens to verified image messages, current event messages, and the latest eleven `userPresence` documents ordered by `lastActiveAt` descending, regardless of age. It excludes the real Firebase Auth user and displays up to ten others; signed-out visitors see the latest ten users. The list reacts to sign-in, sign-out and account changes. Profile queries are bounded to those ten users; missing/unavailable profiles use a neutral fallback. Chat read cursors remain independent.
- Production Home uses `HomeFeedService`: the image query reads at most 50 verified messages ordered by `chatImageTimestamp` and displays up to 25 with image URLs. Event queries retain the existing `lastMessage`, `verified` and future `eventDateEnd` filters, using live pages of 50 with document cursors until exhausted. Home sorts the results by start time and displays the first four still-current events, preserving the original Home selection across page boundaries. Home funds reuse the Q09/I18 active-fund query (`lastMessage == true`, `verified == true`, `fund.active == true`, ordered by `fund.daysLeft` ascending) in live pages limited to 50 records each. Cancelled sub-penny markers, ended funds and missing conversation links are filtered; cursor pages continue only until enough valid funds are found or the query is exhausted. Home initially displays four funds and loads four more on request, using one additional valid result to determine whether Load more is needed. Rows project only fund display fields and conversation links; currency display uses the same conversion and zero-decimal formatting as Chat. Leaving Home unsubscribes from its feed and presence listeners. Existing scalability limitation: event traversal and sparse fund-result traversal have no explicit maximum page count or total read/listener budget; a page limit does not bound total work. Future changes must follow [AGENTS.md → Performance and cost](AGENTS.md#performance-and-cost), agreeing any necessary budget or query redesign without silently truncating required results. These are read-only queries; persisted fields, rules and indexes are unchanged.
- `PresenceService` starts in the app shell and follows real Firebase Auth (not prototype login overrides). It writes on authenticated app opening and when visible, with a five-minute per-tab throttle; visibility and reconnect events can also trigger an update after that interval. Hidden/offline tabs skip new updates. Logout stops future updates and retains the last timestamp. This is approximate recent activity, not online/offline status or an audit of explicit sign-ins; a write already queued during a connection loss may complete later.
- Profile activity reads `userPresence/{userId}` directly, with loading, unavailable and no-record states. It does not fall back to chat cursors. Home and profiles share `formatLastSeen`: “Seen today”, “Seen this week”, “Seen this month”, then “Seen longer ago”, in that order. Boundaries use the viewer's local calendar, with weeks starting Monday; a week spanning a month/year boundary takes precedence over the month bucket. Missing/invalid timestamps show “No activity recorded”; future timestamps are treated as today for clock skew. Existing client clocks refresh labels without polling Firestore.
- Presence records contain only `lastActiveAt`; UID comes from the document ID. Reads are public under the existing broad read grant. Rules allow only owner creates/updates with the server request timestamp and no extra fields; client deletes are denied. No Functions or message schema changes are needed. Deploy the new Firestore rules before releasing the client. No backfill is performed: users appear on their next authenticated visit. The simple presence ordering uses the default single-field index.
- `ImageViewerService` reuses loaded Chat images sorted by `chatImageTimestamp` and document ID. At a carousel edge it queries only the selected thread’s image records: `chain == thread`, `chatImageTimestamp > ''`, ordered by `chatImageTimestamp` descending for older images or ascending for newer images, with full document snapshot cursors and `limit(25)`. Each navigation action fetches at most one page; it never scans ordinary message history or automatically walks further pages. The nonempty-string filter follows existing timestamp-prefixed upload IDs and excludes ordinary messages with absent/null image timestamps. Images missing that metadata remain viewable when clicked, but cannot be discovered through this query; no backfill is performed. One anchor document read starts each direction, and fetched image metadata remains cached until close. The existing descending image index supports older pages; the new ascending `chain`/`chatImageTimestamp`/`__name__` index must be deployed and ready before releasing newer-image paging. No persistent writes or authorization changes are introduced. Navigation/close invalidates in-flight results. Thread links use known record context and display the already-loaded chat subject, preserved while paging within the thread; missing subjects use “Conversation” without an extra query. Profile/account images have no inferred thread. Deleted/missing anchors retain the selected image and offer retry. Invalid image records are filtered locally; if an entire full page has no usable URLs, the next navigation action continues from its cursor rather than fetching more automatically.
- There is no single typed schema for `PERRINNMessages`; the client uses `any` in several places and Functions mutate records after creation. Search exact field names across `src/app`, `functions`, and the rules before changing message fields.
- `PERRINNTeams/{userId}/payments/{orderId}` is written from multiple server-side paths. Preserve idempotency flags and status transition handling when editing payment processing.

### Message activity indicators

The sidebar profile publishes the dot state of its currently loaded conversation rows to `MessageActivityService`. The summary and Home’s mentioned-chat list perform no additional Firebase queries. Home shows the three newest distinct loaded chats whose latest message has an unread name match, with the message preview and propagated chat profile image. Missing or failed chat images use a title initial. The panel is hidden when signed out, shows a compact, muted “You're all caught up.” line when the loaded chats have no unread mentions, and shows loading or unavailable states while account/profile/cursor state is pending or on conversation/cursor errors. Opening a row uses the existing chat route and read-cursor behavior. “Load more” expands its scope; conversations outside the loaded list do not contribute. Cursor, profile and authentication changes recalculate the summary using the same conditions as the row template.

`SidebarConversationsService` retains unflagged legacy records and excludes only latest messages with `isBackendMessage === true` from the main sidebar. It traverses live pages of 30 verified latest messages ordered by descending `serverTimestamp`, using document cursors until it fills the requested human-chat count (initially 30, increasing by 15 on Load more) or exhausts the query. Each page is limited to 30 records, but automatic traversal has no explicit maximum page count or total read/listener budget; total work grows with intervening automatic records. This is an existing scalability limitation, not a recommended pagination pattern. Future changes must follow [AGENTS.md → Performance and cost](AGENTS.md#performance-and-cost), agreeing any necessary budget or query redesign without silently omitting required conversations. Page boundary changes replace downstream subscriptions, and destroying the sidebar unsubscribes all pages. Filtering happens before read-cursor listeners are attached. `MessageActivityService` also excludes flagged backend records defensively, including manual flags. Existing profile feeds and full chat history retain their previous behavior.

Automatic updates use a separate live query for verified latest messages with `isBackendMessage == true`, descending `serverTimestamp`, limited to 15. Presentation, dimensions, scrolling and accessible states follow [ui-spec.md → Responsive](ui-spec.md#responsive). Query states are independent of human activity tracking. Each chat belongs to the list selected by its latest message; a human reply moves it back to the main list. Existing unflagged backend messages stay in the main list until a newly flagged message becomes the latest. The query has no additional read-cursor listeners and contributes no activity dots or Home mentions. The new Functions and index must be deployed before the client; this change does not deploy or backfill anything.

The PERRINN desktop/mobile navigation shows only the highest-priority unread dot: red for a latest-message name match, otherwise green for an unread latest message addressed to the user, otherwise grey for other unread activity. Gold independently indicates a manually flagged loaded conversation. Reading the final conversation in a category removes that summary dot or reveals the next priority. Signed-out users see no dots. No persisted data or rules change is required.

`ReadCursorService` creates a cursor session per profile and for the open chat. The chat header provides a subtle flag toggle beside the subject, replacing the conversation-list flag menu. It merges the existing `blueFlag` and `updatedAt` fields into the current user’s cursor document, preserving read position; the sidebar continues to show flagged conversations. Sessions reuse document listeners for loaded chains, add listeners on “Load more,” and remove listeners for departed chains. Account changes replace all listeners; component destruction unsubscribes them. Missing documents mean no read cursor or flag. Pending reads suppress dot calculations; failures remain unavailable rather than being treated as missing cursors. No cursor collection query is used.

### Maintaining indexes

- Treat `firestore.indexes.json` as the desired configuration for every composite index. Update it alongside client or Functions queries and update this coverage map when a query shape changes. Sync any intentional Firebase Console additions back into the file. Firebase documents this workflow in [Managing indexes](https://firebase.google.com/docs/firestore/query-data/indexing).
- Recheck query plans when filters/orderings change. Keep indexes used through index merging as well as direct selections; a missing exact composite match does not prove that a query is unsupported.
- Before deployment, export live indexes and compare them with the desired file. Review additions and deletions explicitly; an index deployment may prompt to delete live definitions absent from the file. The dated audit exports are evidence only and are not deployment configuration.
- Deploy required additions and wait for readiness before releasing dependent queries. Deploy obsolete-index deletions only within an explicitly authorized cleanup/deployment scope. Preserve a live export for recovery; recreating deleted indexes can take time.

### Chat transfer commands

The Chat PRN manager uses the existing `PERRINNMessages` create contract: `user`, `name`, `imageUrlThumbUser`, server `serverTimestamp`, `chain`, `text`, and either `transactionOut: { user, amount, code, reference }` or `transactionPending: { amount, code, reference }`. `amount` is PRN, rounded to five decimal places. No new fields or paths are added. `dbMessagesOnCreate` / `verifyMessage` retain their existing verification, debit/credit and activation behavior.

`prnTransfer.service.ts` refreshes two bounded reads at review and again before a new submission: the latest sender record (`user == uid`, `verified == true`, `serverTimestamp DESC`, limit 1; Q18/I55) and latest conversation record (`chain == chain`, `serverTimestamp DESC`, limit 1; Q03/I02). It requires the latest conversation to be verified. It reads the reviewed message document by ID before confirmation/retry; an existing matching command is acknowledged rather than rewritten. Each review allocates one message ID without writing. The retry identity lives only in that open review, so closing/navigating away does not provide cross-session duplicate prevention. A pending transfer reserves no funds.

Balance, rate, account and recipient checks in this client service do not add server authorization. The current verifier does not enforce sufficient balance atomically, and pending activation retains its existing access assumptions. Hardening those handlers is separate backend work. Chat flags retain the existing `blueFlag` field and profile links/mention emphasis add no persisted state.

Chat transfer presentation projects only positive finite per-message transfer amounts, party names, references, optional codes, verification status and pending activation state. The message list builds a map of its already-loaded records to enrich a receipt from `transactionIn.message`; it accepts source details only when chain, sender, recipient and amount match. Missing older sources do not trigger additional reads. Stored text, transaction processing and schemas are unchanged. Raw wallet/email/cumulative fields remain excluded from the message view model.

### Per-message time credits in chat

The chat message view projects the existing `contract.amount`, `contract.hoursValidated`, `contract.hoursDeclared` and remaining declaration allowance into a compact time-credit note. Only `verified == true` records with positive finite earned amounts and validated hours show an award. The earned amount uses the shared PRN formatter in the viewer's selected currency (including its existing signed-out USD fallback); this converts presentation only. No credits are inferred from leading `>` characters or recalculated from current hourly rates. Optional missing/invalid historical declaration and window values are omitted; raw contracts, signature IDs, cumulative totals and wallets remain outside the message view model.

`hoursAvailable` is the declaration allowance before that message's declaration. The note shows the allowance left afterward, using `previousContractMessageHoursAvailable` when valid, or `max(0, hoursAvailable - hoursValidated)` for older records. It is explicitly labelled as the allowance after this message, not today's remaining allowance or elapsed wall-clock time. The existing verifier replenishes this moving allowance at the configured `hoursAvailable24HoursWindow / 24` hourly rate, caps it at `hoursAvailable24HoursWindow`, validates `min(hoursDeclared, hoursAvailable)` and computes `amount = hoursValidated * hourlyRate`. The client does not change validation or earned credits. Durations display hours/minutes rounded to a minute, with positive sub-minute durations shown as `<1 min`. Records and message text are unchanged, and no queries, rules, indexes or Functions change.

## Greenpower telemetry

Issue #95 adds an isolated `GreenpowerTelemetry` root collection. User-approved scope includes permanent raw retention, daily history and charts, with all viewing (including GPS) restricted to real signed-in users. No membership, balance or role threshold is involved. Existing message/payment/profile workflows are unchanged. Phone setup and validation are in [README.md → 424 Greenpower Telemetry](README.md#424-greenpower-telemetry).

| Path | Fields / purpose |
| --- | --- |
| `GreenpowerTelemetry/424/days/{YYYY-MM-DD}` | `date`, `activeChunk` (zero-based integer), `count`, `latest` sample, `updatedAt` (server timestamp) |
| `…/days/{date}/chunks/{10-digit zero-padded index}` | `samples` array and `bytes` (serialized sample bytes) |
| `GreenpowerTelemetry/424/config/view` | `scalars`, `charts` (maps from stable channel ID to boolean true, at most 512 entries each); `scalarOrder`, `chartOrder` (optional ordered channel-ID arrays); `revision` (positive integer); `updatedBy` (saving admin UID); `updatedAt` (server timestamp) |
| Each sample | `id` (server UUID), `receivedAt` (server wall-clock epoch milliseconds), `source: '424-phone'` (credential-bound source), `raw` (original JSON string) |

`functions/greenpowerTelemetry.f.js` exports the HTTPS `greenpowerTelemetry` handler through `functions/main.js`; validation and transactional append logic live in `functions/utils/greenpowerTelemetry.js`. Only this handler writes these paths. One accepted request creates one sample. The original JSON preserves unknown keys, arrays, source timestamps, values and units without exposing them to Firestore nested-array restrictions. Dates are derived from server receipt time in Europe/London, never the viewer timezone or an unverified source-time field. Concurrent transaction completion may differ from receipt ordering; the client sorts points by receipt time and metadata's latest sample never regresses to an earlier receipt time. There is no automatic deletion, TTL or historical import. Retries without a source-stable sample ID are retained as separate receptions.

The shared view document is separate from retained telemetry. Its two maps independently select scalar/chart channel IDs already produced by `greenpowerData` (JSON field path plus explicit/native unit). All values must be boolean true; rules enforce map type, 512 entries per section, an exact top-level field allowlist, the saving account's UID, server request time, revision 1 on create and an increment of exactly one on update. Clients additionally validate ID byte lengths (Firestore's 1,500-byte field-name limit) and configuration shape. Optional `scalarOrder` and `chartOrder` arrays define independent display order. When present, each must be a list containing exactly the selected map keys once, with no missing, duplicate or extra IDs; the 512-entry map bound also bounds each order. Without an order field, legacy selections retain their prior sorted channel-ID order. New editor saves write both arrays together with the existing selection maps and revision; no automatic data migration is required. Older clients can still save the legacy shape, which restores the legacy sorted order for any omitted array. Missing scalar channels show a dash; missing/non-numeric chart channels produce no chart. The editor retains missing selections for removal or reordering, using their field paths/units for labels. Available new channels come only from already-loaded telemetry; no channel-catalog scan or ingestion change is introduced.

`GreenpowerViewService` adds one fixed document listener for each open signed-in page, independent of day/history switches; it stops on sign-out, account change and destruction. Cache-only or locally pending snapshots never authorize/display configuration. Before a server snapshot, or after load/validation failure, the shared view stays unavailable with retry rather than exposing a stale local layout. A missing server document preserves the original all-channel layout. An existing document is an explicit allowlist: unselected/new channels stay hidden until an admin saves them. Hiding channels changes neither ingestion/retention nor the existing raw-history read budget.

Draft editing, including pointer/keyboard reordering, performs no database work. A drag handle owns its touch gesture, while other list areas retain native scrolling. Edge scrolling runs only during an active drag, at up to 400 CSS pixels/second, and stops at the list boundary, release or cancellation. Reordering is limited to the selected section (at most 512 channels); cancellation restores its original valid draft order. No new persisted fields, queries or listeners are introduced by drag sorting. Save uses a transaction with at most three document-read attempts and one committed configuration write, checking the revision captured when editing began. A fourth SDK callback is rejected before reading; there is no custom background retry loop. A stale revision preserves the local draft and asks the admin to cancel/reopen. Sign-out/role loss cancels drafts; in-flight reads check the account generation again before scheduling a write. The successful transaction acknowledgement updates the saving editor immediately, so reopening before its listener catches up uses the committed revision; older listener revisions cannot regress that confirmed state. Every viewer receives the resulting server snapshot. Listener reconnects can reread the single settings document; the Firebase 1 MiB document limit remains the maximum snapshot size. No collection query, new composite index, per-user settings, automatic history scan or periodic configuration polling is added.

Input limits are 16 KiB UTF-8 JSON object, at most eight nesting levels and 512 leaf values, with keys at most 128 characters and finite numbers. Invalid requests return 400, invalid authentication 401, unsupported methods 405, unsupported POST content types 415 and storage failures 503. Successful writes return 204 only after commit. The Function requires Basic credentials (`424` plus Secret Manager password); neither credentials nor request payload/URL/provider errors are logged by application code. Documented GET payloads appear in request URLs and can consequently be present in platform request logs: do not put credentials in URLs. OMNI's actual method/authentication/frequency/retry contract must still be checked on the installed phone. No credential is stored in Firestore or browser configuration.

Each chunk contains at most 32 samples and 128 KiB of serialized sample content. Each ingestion transaction reads the day and active chunk and commits two writes (day + chunk); max three attempts means up to six document reads under contention, with two committed document writes per accepted request. Function configuration caps concurrency at ten per instance, two instances and a 15-second timeout; these cap simultaneous server work, not total daily ingestion or spend. Platform overload/network failure can reject requests; the phone's retry/buffering behavior is unknown. All accepted requests are retained permanently, so total storage and operating cost grow with usage.

At the working three-second interval, a 24-hour day yields 28,800 samples, 900 chunks if the count limit is reached first, and 57,600 committed writes plus at least 57,600 transaction reads. The 23/25-hour UK clock-change days yield 27,600/30,000 samples (863/938 count-limited chunks). Large payloads roll chunks earlier. These are volume estimates, not measured operating costs or a guaranteed phone rate.

The client loads history in ascending chunk-ID pages of at most 100, with a maximum of 50 requests/5,000 fetched chunks or 64 MiB of serialized chunk data per loading action. Request limits also shrink to the remaining byte budget using the conservative 132 KiB per-chunk wire-content estimate; SDK/protocol overhead is additional. Pages overlap their mutable boundary chunk, so a normal 900-chunk day requires ten chunk queries and 909 document reads, plus one day metadata read/listener and an initial overlapping tail read. At a budget boundary, the page explicitly offers Load remaining data, without discarding retained samples or pretending the day is complete. Another click grants another bounded action. Date-list loading is exactly one query of at most 30 days per user action, with a cursor for Earlier dates. Empty results stop immediately; failures do not trigger a custom retry loop.

Live uses one day-document listener plus one chunk-tail listener with limit 100. On filling that window, it replaces only the tail listener with an overlapping window; it permits at most 50 windows and 64 MiB of newly accumulated sample content per loading action before requiring explicit continuation. Metadata still supplies current scalar values while chart history awaits continuation. Tail updates replace cached mutable chunks instead of duplicating samples. Only changed chunks are parsed again; chart paths preserve up to two extrema per horizontal pixel bin; all original samples remain available for cursor inspection. Rewritten chunks and metadata are billed/transferred on updates, and Firebase SDK reconnects may reread listener results; the history byte budget is not a cap on session network traffic or billable reads. Continuous listeners last only while this routed component is alive and signed in. UK midnight switches Live to the new day. Date changes, account changes, sign-out and destruction unsubscribe listeners and invalidate pending responses; an already-issued server read may still complete but is not rendered. There is no polling or background retention job.

History queries use `source: 'server'`, and live snapshots from local cache are not rendered before server authorization. Sign-out clears in-memory values and dates. The existing app-wide Firestore IndexedDB persistence setting is unchanged: previously authorized records may remain in that device's SDK cache. This does not provide device-storage encryption or remote erasure.

`firestore.rules` excludes only this root collection from the old recursive public-read grant, then grants its reads when `request.auth != null`. Client writes are denied except create/update of the exact `GreenpowerTelemetry/424/config/view` document by a token with `perrinnAdmin == true`; deletes remain denied. Admin ingestion bypasses rules after authenticating the phone. Tests verify anonymous denial, two different signed-in readers, denied client writes and preservation of other collections' existing public reads. This is an intentionally isolated change, not a remediation of the legacy access issues documented earlier.

The HTTPS ingestion service permits public transport invocation and authenticates every request in the application. Its underlying Cloud Run `greenpowertelemetry` service must have `invokerIamDisabled: true`: the default IAM check rejects Basic Authorization headers before the handler, even with an existing `allUsers` invoker grant. This configuration implements the approved phone credential contract; it does not grant Firestore reads/writes or bypass the application's credential validation. Deployment instructions are in README.md; the setting is isolated to this service.

No composite index is added/deleted: chunk and date queries order only by document ID. `firestore.indexes.json` adds automatic-index exemptions for `days.latest` and `chunks.samples`, which are payload fields with no query readers in this repository. As field overrides operate by collection-group name, inspect live uses of those names and complete the [index audit](#firestore-index-audit) before deployment; do not delete unrelated live indexes. Deploy rules before accepting real phone data so the existing live wildcard cannot expose new documents. The [19 October predeployment audit](audits/greenpower-predeploy-2026-10-19.json) found all 19 live composite indexes matched the repository with no additions/deletions; live rules matched the baseline. Two collection-group queries projected document names only, each limited to one result; both `days` and `chunks` were empty, so the new field exemptions affect no existing records. The [live index export](audits/greenpower-indexes-2026-10-19.json) is retained as recovery evidence. Production deployment follows validation, commit and push; emulator results alone do not establish live behavior.

## Team Radio prototype (Realtime Database)

The isolated `/teamRadio/team` subtree is used only by `/prototypes/team-radio`. It uses real Firebase Auth, not prototype identity overrides. It introduces no Firestore paths, indexes, Functions handlers, recording or audio storage. Existing app data and authorization remain unchanged.

| Path below `/teamRadio/team` | Shape and lifetime |
| --- | --- |
| `seats/{0..9}` | `{uid, name}`; one active place per account, first authorized atomic claim wins. Name reuses the already-loaded PERRINN profile only when its `user` matches real Auth UID, otherwise resolves the latest verified user message with `limit(1)` (existing Q18/I55 index). Auth display name or Contributor plus a short UID is the fallback; only the display name is copied to RTDB. Claimed atomically with fresh presence; released after the three-minute away window, sign-out or stale-session recovery. |
| `speakers/{0..2}` | `{uid, seat}`; optional speaking place for a joined participant. One per account; released with the participant place after away expiry, sign-out or stale-session recovery. |
| `presence/{seat}` | `{session, online, at, muted, ready}`; newest audio tab replaces the account's previous session. Server timestamp heartbeat every five seconds; twenty seconds without a heartbeat is treated as offline. `ready` means the browser audio context is running and expected peer connections are connected, not proof that a person heard audio. |
| `floor` | `{uid, seat, session, token, startedAt, expiresAt}`; one active speaker, acquired transactionally after readiness checks. Thirty-second maximum lease; never renewed by holding the key. A vanished/replaced/offline/stale session invalidates it while exit cleanup and stale recovery free places separately. |
| `signals/{recipientSeat}/{senderSeat}` | `{fromSession, toSession, offerId, type, sdp}`; one bounded SDP record per direction per seat pair (at most 90). Sessions bind the message to current connections. Replaced on negotiation, deleted in both directions on session cleanup. Only its recipient can read a mailbox; only the sending account can create/update its records. |

`database.rules.json` restricts radio reads to authenticated users and signaling reads to the intended account. Writes enforce fixed slot keys, unique account reservations against the proposed final state (including multi-path writes), field allowlists, ownership, speaker membership, live sessions, a 30-second floor lease and SDP size bounds. Other database paths remain denied. A client cannot remove its participant reservation while retaining a speaking reservation. There is no administrator eviction or queue. Signed-in users may remove another account's place only when its heartbeat is absent or at least 180 seconds old, removing its speaking place in the same atomic update. Orphan speaking places can also be reclaimed; fresh cross-user places cannot be removed.

Each claim writes the participant and initial online presence atomically, enforcing a fresh server timestamp. Heartbeats run every five seconds. Away expiry and auth changes stop media and attempt one atomic cleanup of the participant, speaking place, signaling and a matching offline presence tombstone. The tombstone session check rejects the entire update from an older tab if a newer tab has taken over. Heartbeats also check the current session before updating.

Firebase disconnect updates are checked per path, so cross-path participant/speaker consistency prevents registering that atomic cleanup as an `onDisconnect` operation. Instead the server registers only the matching session's offline tombstone. Connected clients reclaim missing/stale heartbeat places every five seconds and before claims, after the three-minute grace period. Server reclamation uses the last server presence timestamp (including offline marking), so removal is eventual and may lag the local deadline by disconnect detection and the five-second recovery interval. This also recovers the brief claim-to-disconnect-registration gap. Cached own-account places are not reclaimed by the periodic worker, preventing old snapshots from removing a newer own session. Automatic admission on the visible radio page replaces an unrecoverable old own session and returns as a listener. Admission waits for Auth, connectivity and the complete roster, never requests microphone permission, and waits for room capacity without a queue. A brief network loss preserves the local participant and speaking places, removes peer audio paths, and gates the microphone off. Its local grace deadline is three minutes after detected loss; repeated disconnect notifications do not extend it. A permitted microphone and audio context remain open during this grace period to allow automatic recovery without another microphone request; network/away expiry or sign-out stops the capture tracks. No outage audio is recorded or replayed. No new fields or Functions are introduced. Existing offline reservations are eligible for recovery; older clients must refresh before new claims because the rules now require atomic initial presence.

Control is fail-closed on database disconnect: outgoing and received audio stop immediately. Within the three-minute local grace deadline, a server-checked presence transaction confirms the previous session still owns the place, rotates the audio session, refreshes presence and re-registers disconnect cleanup before restoring peer connections. Existing speaking permission is retained. A fresh press is required to transmit; an old floor token or SDP cannot become active in the new audio session. Expired sessions can rejoin automatically as listeners when the radio page is active and connected. Superseded sessions stop rather than repeatedly taking over from another tab. Receivers accept only the current authorized floor session, and recheck expiry and presence. WebRTC transports audio outside Firebase; the prototype's browser checks are not a trusted media server and cannot prevent modified clients from sharing already-received audio elsewhere. No additional server-side media enforcement is claimed.

SDP includes ICE connection metadata, not recorded audio. Session cleanup removes signaling records for that seat; abrupt disconnect can leave bounded session-stale records to be overwritten on a future claim. Transmit tokens prevent late release/cleanup from clearing a newer transmission. Space is hard-coded; the radio stores no keyboard preference. There is no relay credential form or additional radio login; radio authorization uses the existing PERRINN Auth session. Test using `npm run test:radio` and `npm run test:radio:rules` against a local database emulator; see [prototypes.md](PROTOTYPES.md#team-radio).

Team Radio participant photos use `RadioAvatarsService` and the shared `app-user-avatar` component. The current user's already-loaded profile is reused only when its UID matches real Auth; other participants use bounded latest-verified-profile queries (`limit(1)`, at most ten active participant identities, Q18/I55). Photo subscriptions are removed when participants leave the roster. Stored photo candidates follow the existing thumbnail/medium/original order and shared placeholder filtering, with the normal initials fallback for missing/failed images. No avatar fields are copied into Realtime Database.

The radio page no longer owns the room/audio providers. `RadioLifecycleService` retains a scoped instance for up to three minutes while another PERRINN route is open or the radio page is backgrounded. Listening continues while supported; transmission always stops when the page becomes inactive. Returning before expiry cancels the away timer. An overlapping network timeout cannot extend that timer; the earlier deadline ends the session. Expired off-page instances are destroyed so their Firebase listeners, media and timers do not remain active throughout the app.

The browser tab stores one `sessionStorage['perrinn.teamRadio.return']` record `{uid, seat, session, until}`. It contains an account ID, an opaque radio session ID, the fixed seat key and a local expiry timestamp, with no credentials, profile or audio data. Active references renew no more than once every five seconds; away/network references retain their deadline. Pagehide preserves the reference and suspends audio instead of deleting places. Same-tab reload/back restoration waits for real Auth and all three bounded roster snapshots, checks UID/seat/session/expiry, then uses the existing server-checked presence transaction to rotate the audio session while retaining any speaking role. A reference alone does not authorize a claim or recreate a removed place. Expiry, sign-out, a different account or failed ownership confirmation clears it. Storage denial disables reload restoration but preserves normal in-app navigation. Firebase shapes, rules and Functions remain unchanged.
