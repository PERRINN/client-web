# PERRINN

PERRINN is a contributor collaboration app for profiles and contributor discovery, conversations, account settings, PRN contribution accounting and funding flows, and community information.

## What’s in the app

- **Profiles and Team** for finding people and viewing their contributions.
- **Chat** for conversations and community activity.
- **Account settings** for profile and account details.
- **PRN Contribution Credits** pages for contribution recognition, balances, transfers, time credits, and project funding.
- **Community information** and links to related resources.

The main client routes are `/home`, `/profile/:id`, `/team`, `/apps`, `/chat/:id`, `/settings`, `/login`, and `/buyPRN/:id`. The root route redirects to `/home`. The legacy `/directory` URL redirects to `/team`. Both desktop and mobile PERRINN brand controls open Home. Funds initially shows four entries ordered by days remaining, with Load more for additional entries; each opens its conversation. Fund amounts and days display rounded to whole numbers. Touch-device visitors outside standalone mode also see a subtle home-screen tip above the banner; dismissing it hides it for the current tab session. The PERRINN profile banner appears above the headline using the already-loaded profile image; unavailable or failed images are omitted. It adapts to available width without prototype navigation or manual resizing.

## Keep the screen awake

The installed Home Screen app automatically requests a screen wake lock on every page while visible. Ordinary browser tabs opt in using **Settings → Keep screen on**. The switch enables or disables the request; it does not claim that the phone granted it. There is no persistent header control or status. Settings shows **Couldn’t keep screen on.** if the phone/browser refuses or releases the request, or **Not supported by this browser.** when unavailable. That choice lasts until the app reloads/restarts; no preference is saved to an account or device storage. A granted screen wake lock inhibits inactivity-based dimming and automatic screen locking.

Backgrounding/leaving releases the lock; returning restores it if still enabled. One root service owns the lock across routes, serializes requests and releases late grants after cancellation. There are no timers, polling, backend requests or database operations. The OS can override the request for power saving, and the feature does not prevent a manual lock or control the brightness level/automatic brightness. Idle dimming and locking use the same `screen` request; there is no separate dimming API or switch. See the [Screen Wake Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API). Keeping the display on consumes battery; real-device auto-lock and foreground recovery still need checking on the race phone, including the installed iPhone app.

Validate with `npm run test:screen-wake-lock`, build and lint. For synthetic browser lifecycle/layout checks, run `node scripts/greenpower/launch-preview.mjs`, then `node scripts/screen-wake-lock-ui.mjs` (set `PLAYWRIGHT_MODULE`/`PLAYWRIGHT_CHANNEL` for an external browser runtime). This uses the real shell/service with synthetic wake-lock grants, no Firebase access, and checks desktop, portrait and landscape layouts. It does not establish physical-phone behavior.

## Configuration and secrets

The client Firebase web app configuration is selected through Angular environment files:

- `src/environments/environment.dev.ts` for local development.
- `src/environments/environment.prod.ts` for production builds.

Browser environment values are included in the client bundle and must be treated as public configuration, not secrets. Do not put service account credentials, payment provider keys, or other privileged values in client files. Cloud Functions read privileged integration credentials through Firebase Functions secrets. Keep those values in the project's approved secret management setup and never add them to this README or source control.

424 Nürburgring Telemetry records 43 channels and displays 33 analysis charts with vertical scales fitted to each visible window. Flap angle (degrees) and DRS position (0–100%) appear immediately before the aero coefficient charts in new recordings; older recordings retain their original channels. It refreshes the Angular display at 10 Hz. Missing channels remain unavailable. Front spring rate sets both front wheels in N/m; autopilot position offset is in metres. Controls show Unity-confirmed values and command results. Input bounds are 10,000–1,000,000 N/m and −10–10 m; these are input guards, not validated vehicle operating limits.

Changes last until the bridge stops, when original settings are restored. Disconnecting the browser does not restore settings. Reconnection reads current parameters and never replays commands; a new Unity session requires its new token. Simulation pause through time scale/vehicle pause allows commands, while the Editor Pause button suspends update handling. The folder appears in the Unity inspector. Each session contains `session.json`, `samples.bin` and `changes.jsonl`; normal bridge shutdown flushes the recording and marks it complete. No recordings are uploaded to Firebase. Browser memory retains all samples while this page is open; reconnect catches up from the active Unity session.
